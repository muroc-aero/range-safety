# Literature Review: Assurance of Agent-Driven Engineering Analyses

Where range-safety sits in the literature, organized around the six research
areas adjacent to what the package does (pre-run plan validation, post-run
convergence/constraint assertions, provenance-backed lifecycle replay) and
where it is heading (the directions in `DESIGN_DIRECTIONS.md`: runtime
guardrails, independent adversarial verification, certification-as-code,
probabilistic verdicts, event-sourced replay, push observers).

For each area: the key works, what they established, and the gap a system
like range-safety addresses. A cross-reference table at the end maps
literature gaps to our design directions.

> **Provenance of this document.** Compiled 2026-07-10 from a fan-out web
> search (5 angles, 20 sources) with per-source claim extraction (78 claims,
> each backed by a verbatim quote from the source). The planned adversarial

> plus editorial judgment, not independent cross-checking. Items marked
> *(unverified)* are recent preprints whose details we quote but have not
> corroborated; treat exact figures from those with care.

## 1. W3C PROV and workflow provenance for computational science

**Key works.**

- **W3C PROV-DM** (W3C Recommendation, 2013) — the conceptual data model
  behind the PROV family: Entities, Activities, and Agents connected by
  `wasGeneratedBy`, `used`, `wasDerivedFrom`, `wasAssociatedWith`. Its stated
  purpose is to record who/what/how so consumers can "assess the data's
  quality, reliability, or trustworthiness." Notably, PROV defines an agent
  by *responsibility* rather than humanity, explicitly admits software agents
  ("a software agent is running software"), and lets agents themselves be
  entities so the provenance *of the agent* (versions, configuration) is
  expressible. https://www.w3.org/TR/prov-dm/
- **Provenance analytics survey** (Oliveira et al., ACM Computing Surveys,
  2018) — establishes that capture and storage are largely solved by
  scientific workflow management systems; the open bottleneck is *analysis*:
  "how to analyze the large amounts of provenance data generated by workflow
  executions and how to extract useful knowledge of this data."
  https://dl.acm.org/doi/10.1145/3184900
- **ProvLake / lifecycle provenance for scientific ML** (Souza et al., CCPE
  2022) — a W3C-PROV-compliant representation and reference architecture
  spanning a full computational-science + ML lifecycle, with evidence that
  always-on capture is cheap (<1% overhead in an HPC oil-and-gas evaluation).
  https://arxiv.org/abs/2010.00330
- **PROV-AGENT** (Souza et al., IEEE e-Science 2025) — extends W3C PROV with
  Model Context Protocol (MCP) concepts so agent prompts, responses, tool
  calls, and decisions become first-class provenance alongside workflow
  tasks. Its motivating failure mode is ours verbatim: "agents can
  hallucinate or reason incorrectly, propagating errors when one agent's
  output becomes another's input." *(unverified)*
  https://arxiv.org/abs/2508.02866
- **Flowcept** (ORNL) — open-source runtime provenance capture for AI and
  scientific workflows (including MCP agents), streaming provenance through a
  pub-sub hub across edge/cloud/HPC, claiming W3C PROV adherence.
  https://github.com/ORNL/flowcept
- **LLM agents over provenance** (Souza et al., 2025) — puts interactive LLM
  agents *on top of* provenance stores, translating natural-language
  questions into structured provenance queries at runtime; built on Flowcept.
  *(unverified)* https://arxiv.org/abs/2509.13978

**What's established.** A standard vocabulary exists that our lifecycle maps
onto cleanly (the Hangar provenance stores are already PROV-flavored:
entities, activities, `wasDerivedFrom`, `satisfies`/`violates` edges).
Capture is a solved, cheap problem; agent-centric capture (prompts,
decisions, tool calls) is now an active frontier with a named model
(PROV-AGENT) and a running system (Flowcept). Even our "conversational layer
over the read model" idea (`DESIGN_chase_plane.md`) has direct precedent in
the LLM-agents-over-provenance work.

**The gap range-safety addresses.** The literature records and queries;
it does not *judge*. Nothing in this area runs requirement-aware assertions
over the captured graph, derives lifecycle state (our five-stage machine), or
produces verdicts. The ACM survey's "analysis bottleneck" is exactly the slot
range-safety's read model + assertions occupy — and doing it for MDAO
specifically (plans, DVs, constraints, convergence) rather than generic
workflow traces.

## 2. V&V standards and practice for computational engineering models

**Key works.**

- **AIAA G-077-1998** — the first formal V&V guide in aerospace CFD;
  established the now-standard verification-vs-validation definitions and
  credibility-building philosophy inherited by everything after.
- **ASME V&V 10 / V&V 20 / V&V 40** — the standards family. V&V 20 (CFD and
  heat transfer) supplies the quantitative machinery: validation comparison
  error `E = S − D` and validation uncertainty `u_val` combining numerical,
  input, and experimental uncertainty. V&V 40 (developed for medical devices)
  contributes the *risk-informed credibility* framework: rigor scaled to
  model risk = decision influence × consequence, with graded credibility
  factors. Survey of the whole landscape: Standards and Methods for V&V and
  Uncertainty Assessments (ASME J. Verif. Valid. Uncert., 2020) — which also
  notes the standards focus on grid-based discretizations and that
  numerical-uncertainty procedure development is still ongoing.
  https://asmedigitalcollection.asme.org/verification/article/5/2/021001/1083913/Standards-and-Methods-for-Verification-Validation
- **NASA-STD-7009B** (2024) — NASA's models-and-simulations standard; defines
  the Credibility Assessment Scale (verification, validation, input pedigree,
  results uncertainty, results robustness, use history) and requirements for
  reporting M&S credibility to decision makers.
  https://standards.nasa.gov/sites/default/files/standards/NASA/B/1/NASA-STD-7009B-Final-3-5-2024.pdf
- **Oberkampf & Roy, *Verification and Validation in Scientific Computing***
  (Cambridge, 2010) — the canonical technical reference: code verification
  (manufactured solutions), solution verification (discretization-error
  estimation, Roache's Grid Convergence Index), validation metrics (incl.
  the area metric), and predictive capability, for exactly the PDE-based
  model class (aero/structures/propulsion) the Hangar tools wrap.
  https://www.cambridge.org/core/books/verification-and-validation-in-scientific-computing/05CA1F8F3CCB5AE5445FDF55239A0183

**What's established.** Thirty-plus years of mature method: we do not need to
invent what "converged," "verified," or "credible" mean. The taxonomy (code
verification / solution verification / validation), the quantitative metrics
(GCI, `E`, `u_val`), and even a graded credibility scale (NASA CAS) all
exist. This is the technical content behind our `assertions/` package and
the roadmap toward probabilistic verdicts (Direction 4): GCI and `u_val` are
precisely the "defensible likelihood terms" `DESIGN_DIRECTIONS.md` calls for.

**The gap range-safety addresses.** Every one of these standards assumes a
*human* executes the process per study — V&V is a documentation and review
exercise, performed occasionally, on flagship models. None contemplate
per-run, automated execution, and none address workflow- or agent-level
assurance (the ASME survey explicitly scopes to grid-based discretizations).
Range-safety's bet is that when an agent runs fifty analyses a day, the
standards' content must become *machine-executed checks with recorded
evidence* — encoding V&V 20's math as assertions, V&V 40's risk-scaled rigor
as tiered verification depth, and NASA's CAS as a per-study scored artifact.

## 3. Safety/assurance cases and machine-checkable certification

**Key works.**

- **AdvoCATE** (Denney, Pai, Pohl — NASA Ames, SAFECOMP 2012) — the canonical
  assurance-case automation toolset: GSN-standard-compliant argument
  structures, automated pattern instantiation, *composition with
  auto-generated safety-case fragments* (e.g. from the AutoCert formal
  verifier), argument verification, and quantitative safety-case metrics.
  https://link.springer.com/chapter/10.1007/978-3-642-33675-1_2
- **Dynamic Assurance Cases** (Asaadi, Denney, Menzies, Pai, Petroff — IEEE
  Computer, 2020) — assurance cases with runtime "assurance measures":
  probabilistic confidence quantities updated from operational evidence,
  demonstrated on an ML-perception autonomous-taxiing UAS. Lifecycle
  assurance rather than a one-time pre-deployment certificate.
  https://www.researchgate.net/publication/346450817_Dynamic_Assurance_Cases_A_Pathway_to_Trusted_Autonomy
- **ENTRUST** (Calinescu et al.) — GSN assurance cases whose arguments and
  evidence are partially *re-generated and re-verified at runtime* as a
  self-adaptive system reconfigures. https://arxiv.org/pdf/1703.06350
- **Continuous Assurance Framework** (2025) — argues that separating
  development-time from runtime evidence yields fragmented arguments;
  demonstrates a pipeline that automatically regenerates GSN arguments from
  formal verification artifacts (RoboChart, PRISM) whenever specs or results
  change, preserving traceability. *(unverified)*
  https://arxiv.org/pdf/2511.14805
- **CoDefeater** (2024) — uses LLMs to hunt for *defeaters* (arguments/
  evidence challenging claims) in assurance cases; zero-shot, ChatGPT fully
  identified more than half of human-identified defeaters on two real
  systems and produced novel feasible ones. https://arxiv.org/html/2407.13717v2

**What's established.** Assurance arguments can be tooled, not hand-drawn;
machine-generated evidence can be woven into structured arguments
automatically; arguments can be *living* — regenerated as evidence changes —
and quantified rather than binary. Adversarial review of the argument itself
is automatable (CoDefeater is a direct precedent for our red-team twin
applied at the argument layer).

**The gap range-safety addresses.** The lineage runs from manual arguments →
tool-supported arguments → dynamically regenerated arguments, but the
evidence supply chain is still curated per-system by assurance specialists.
No one compiles an assurance case *from workflow provenance automatically*:
requirements→claims, runs→hashed evidence, assertions→inference rules, with
"study is done when it compiles" as the agent's objective. That is
Direction 3 (certification-as-code), and the DAC/ENTRUST/Continuous-Assurance
line says the field is converging on exactly this shape — for robots and
self-adaptive software, not yet for computational engineering analyses.

## 4. Runtime verification and monitoring of autonomous / LLM agents

**Key works.**

- **AgentSpec** (2025) — a lightweight DSL for runtime constraints on LLM
  agents (triggers, predicates, enforcement) intercepting actions at the
  tool-call level; reports preventing >90% of unsafe code-agent executions
  with millisecond overhead, and finds LLM-generated rules achieve high
  precision but incomplete recall (~71%) — so auto-authored guardrails still
  need human review. *(unverified)* https://arxiv.org/abs/2503.18666
- **AI Control** (Greenblatt et al., 2023) — the foundational
  control-evaluation paper: safety protocols (trusted monitoring, untrusted
  monitoring with anti-collusion, trusted editing, human escalation)
  evaluated against a red team that *intentionally subverts* them; a weaker
  trusted model plus a limited audit budget oversees a stronger untrusted
  one. Also supplies the quantitative framing that monitor false-positive
  rates must be calibrated to the audit budget.
  https://arxiv.org/pdf/2312.06942
- **Evidence tracing / execution provenance survey** (2026) — formally
  defines execution provenance as the typed graph of an agent execution;
  taxonomizes pre-execution checks, in-flight monitoring, and post-execution
  trace verification; argues tool-use safety needs *parameter-level*
  provenance, not just tool-level permission checks; notes most of agent
  execution maps onto standard W3C PROV vocabulary. *(unverified)*
  https://arxiv.org/pdf/2606.04990
- **LLM-as-a-Judge survey** (2024) — the design space for judge reliability:
  consistency improvement, bias mitigation (position, verbosity,
  self-enhancement), meta-evaluation benchmarks; states plainly that judge
  reliability "remains a significant challenge."
  https://arxiv.org/abs/2411.15594 — and a large-scale empirical follow-up
  (21 judges, ~541k judgments) finding high test-retest reliability can
  coexist with severe bias, so single-judge verdicts are not trustworthy
  point estimates. *(unverified)* https://arxiv.org/abs/2606.19544v1
- **Formal policy enforcement for agentic systems** (2026) — formal-methods
  expression and enforcement of tool-call policies beyond conversational
  input/output rails. *(unverified)* https://arxiv.org/pdf/2602.16708

**What's established.** Tool-call-level interception with declarative rules
is practical, cheap, and effective — the architecture Direction 1 (Flight
Termination System) assumes. The control literature legitimizes our framing
of the analysis agent as *untrusted-by-default* and gives evaluated protocol
shapes (trusted monitor + audit budget + escalation) for Direction 2's
independent verification. The judge literature is a caution: an LLM verifier
is itself an instrument that needs calibration, bias mitigation, and
uncertainty — which is why our verify story pairs judges with deterministic
assertions rather than replacing them.

**The gap range-safety addresses.** All of this work targets generic safety
hazards (unsafe code, harmful actions, policy violations). None of it knows
what a *wrong engineering analysis* looks like: an unconverged optimizer
presented as converged, a constraint checked at the wrong operating point, a
conclusion recorded without a verify stage. Range-safety instantiates the
control/guardrail architecture with domain predicates — physics envelopes,
convergence criteria, requirement traceability — where the generic literature
has only content filters.

## 5. LLM/AI agents for engineering design and scientific workflows

**Key works.**

- **LLM-driven MDO agent** (2025) — an LLM agent that constructs and runs
  mechanical MDO workflows, using RAG over verified domain knowledge to
  suppress hallucination. *(unverified)* https://arxiv.org/html/2511.17511
- **Agentic aerodynamic design/optimization framework** (Cinar et al.) —
  synthesizes complex aero MDAO workflows from natural-language commands;
  the closest published analog to agents driving OpenMDAO-style tools.
  https://www.gokcincinar.com/publication/pp-2025-agenticframework/pp-2025-AgenticFramework.pdf
- **Hidden pitfalls of AI-scientist systems** (2025) — documents the failure
  class that motivates this whole package: code that executes successfully
  while implementing the wrong algorithm, and outputs that look quantitative
  without being scientifically meaningful — silent failures invisible to
  "did it run" checks. *(unverified)* https://arxiv.org/html/2509.08713v1
- **Agentic Science survey** (2025) — names the "quality verification gap":
  no scalable mechanisms ensure AI-generated claims are reliable and
  reproducible, and agentic discovery trajectories are stochastic and hard
  to replicate. *(unverified)* https://arxiv.org/pdf/2508.14111

**What's established.** Agents genuinely can drive MDAO and scientific
workflows end-to-end — the capability range-safety exists to oversee is real
and published, not speculative. Equally established: these systems'
characteristic failures are *silent* (plausible-looking wrong answers), and
the field itself names verification as the open gap.

**The gap range-safety addresses.** The agentic-MDAO papers build the pilot;
nobody has built the range. Workflow synthesis is demonstrated without plan
validation, post-run assertion, independent verification, or lifecycle
accountability. Range-safety is, to our knowledge, the only system organized
around the *oversight* half of agentic MDAO — and the AI-scientist failure
taxonomy (runs-but-wrong) is precisely what pre-run structural/traceability
validation plus post-run convergence/constraint assertions are shaped to
catch.

## 6. Reproducibility and event sourcing in scientific computing

**Key works.**

- **ReproZip** (Chirigati et al.) — the canonical environment-capture tool:
  traces system calls to package an experiment's full environment for later
  replay elsewhere.
  https://www.researchgate.net/publication/304021464_ReproZip_Computational_Reproducibility_With_Ease
  Related tradition: container/image pinning (Docker), functional package
  managers (Nix/Guix), and research-object packaging (Whole Tale, Sciunit).
- **From agent loops to deterministic graphs** (2026) — argues for converting
  nondeterministic agent loops into deterministic, replayable execution
  graphs with full lineage; essentially the event-sourced replay design of
  our Direction 5 applied to AI-native work. *(unverified)*
  https://arxiv.org/pdf/2605.06365
- The agentic-science survey (area 5) supplies the motivation from the other
  side: agent trajectories are stochastic, so post-hoc environment capture
  alone cannot make an agent-driven analysis reproducible — the *decision
  sequence* has to be recorded too.

**What's established.** Environment reproducibility is mature tooling:
capturing the bits needed to re-run a computation is solved at several
levels (syscall trace, container, package graph). Event-sourced/replayable
execution for *agents* is emerging as its own thread.

**The gap range-safety addresses.** The classical tools reproduce a *single
computation*; an agent-driven analysis is a computation *tree* — plans,
replans, reruns, decisions — and reproducing the conclusion means replaying
that tree, not one leaf. Direction 5 (the Flight Recorder: hash-chained
event log, replay-as-assertion, counterfactual forks) extends the
reproducibility tradition from "package the environment" to "replay the
lifecycle," with divergence itself as a first-class finding. No existing
system offers replay-divergence as a verification check for engineering
analyses.

## Cross-reference: literature gaps → range-safety design directions

| Literature area | What exists | Named gap | Range-safety response |
|---|---|---|---|
| 1. Provenance | PROV-DM vocabulary; agent-centric capture (PROV-AGENT, Flowcept) | Analysis/judgment over provenance | Shipped: state machine + read model + assertions over provenance |
| 2. V&V standards | GCI, `E`/`u_val`, CAS, risk-scaled credibility | Human-executed, occasional, not per-run | Shipped: automated assertions; Direction 4 encodes GCI/`u_val`/CAS as probabilistic verdicts |
| 3. Assurance cases | Tooled, dynamic, quantified arguments (AdvoCATE → DAC → continuous) | Evidence supply still hand-curated; no compile-from-provenance | Direction 3: certification-as-code compiler over the existing provenance contract |
| 4. Agent runtime control | Tool-call DSL enforcement (AgentSpec); control protocols vs. untrusted models; LLM-judge (with known reliability limits) | Generic hazards only; no engineering-domain predicates | Direction 1 (FTS proxy with physics/convergence envelopes); Direction 2 (red-team twin using control-style protocols) |
| 5. Agentic MDAO / science | Agents synthesize and run MDAO workflows; silent-failure taxonomy; "quality verification gap" named | Verification/oversight layer absent | The package's whole premise; validators + assertions target the runs-but-wrong class |
| 6. Reproducibility | Environment capture (ReproZip et al.); emerging agent-replay work | Reproduces one computation, not a decision lifecycle | Direction 5: event-sourced flight recorder, replay-as-assertion, counterfactual forks |

Two design-level takeaways worth pinning:

1. **We should encode, not invent.** Areas 1–3 hand us vocabularies and
   metrics (PROV, GCI, `u_val`, CAS, GSN) with decades of consensus behind
   them. Range-safety's originality is in *automation and composition* —
   making these run per-study without a human in the loop — not in new
   assurance theory. Where our schemas can align with PROV and GSN terms,
   they should.
2. **The verifier is an instrument too.** The LLM-judge results (reliable ≠
   valid; budget-calibrated monitors) argue for exactly the architecture our
   design docs sketch: deterministic assertions as the backbone, LLM
   verification as an additional adversarial layer with quantified,
   calibrated weight — never a lone oracle.
